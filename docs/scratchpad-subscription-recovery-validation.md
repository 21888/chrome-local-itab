# Scratchpad subscription failure recovery

A backend subscription registration exception previously rejected `Controller.init()` before its read-error handling. The production View's action wrapper consumed the rejected promise, leaving the card and Settings controls in their loading state with no explanation. A synthetic backend reproduces this through the real Store, Controller and View without replacing their outcomes.

The Controller now records a private terminal registration-failure state. Its shared source guard rejects subsequent reads and mutations for that instance. The card and Settings display an English/Chinese instruction to reopen the page, retain readonly/disabled editing, and hide the ineffective Retry action. Ordinary read failures keep their existing retry behavior. No stored content is cleared or changed, and no registration retry is performed automatically. Reopening creates a new instance rather than attempting to infer whether a throwing backend partially registered a listener.

`tests/scratchpad-subscription-recovery.test.js` covers both languages: initial registration failure shows the error instead of loading, zero reads/writes preserve the complete original raw state, direct retry/refresh/mutation calls remain rejected even after the backend recovers, and a fresh View reads the saved text without writing. A subsequent explicit input edit uses the unchanged autosave path and produces exactly one new revision/write. The related View and controller-source suites also pass (140 tests total).

The initial negative run failed on `loading !== error`. A first post-fix test attempt used an unsupported aggregate `host.textContent` property in the DOM model; that fixture assertion was corrected to inspect the actual status node before the passing related run. These are synthetic backend/DOM results, not native page reopening, installed Chrome event registration or persistence/upgrade acceptance. They do not identify or resolve the historical data-loss incident.
