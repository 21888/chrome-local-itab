# 1.1.145 · 导入操作记录的复制与完整恢复保护 / Import-receipt guards for duplication and complete restore

## 新增

- 复制工作区与完整本地备份恢复新增针对配置导入操作记录的准入检查。前次配置导入尚未核验、记录无效或版本不支持时，相关操作会停止并明确提示；可另开对应工作区的只读恢复页检查，不丢弃当前名称或恢复草稿。

## 修复

- 复制工作区在生命周期锁内、创建新副本之前检查源记录。未核验导入不能靠复制绕过；已核验来源的新副本不携带源导入操作身份，但当前配置和完整恢复副本（含先前记录）原样保留，源记录不变。已有专注计时器重置行为保持不变。
- 完整备份的配置恢复在审阅、恢复锁准入及异步恢复副本准备完成后检查操作记录，阻止尚未核验的配置导入被新恢复操作覆盖或改变代际边界。拒绝发生在恢复槽、暂存工作区或登记等写入之前，不自动结清或删除原记录。

## 注意事项

- 旧版单工作区备份只检查明确选择的目的工作区；匹配的部分配置备份检查匹配目的ID；完整工作区范围的配置恢复检查所有当前工作区，包括回收站及将被新拓扑移除的工作区。仅恢复个人模块或全局资料库时不新增此检查。
- 结构有效且已核验的记录仍允许复制和完整恢复，包括核验后又有普通配置编辑的情况。手动配置导入同文件的额外确认规则保持不变。没有导入记录的来源沿用原行为。
- 若原导入仍能与保留内容完全匹配，可先通过设置页原文件流程核验；发生不一致的冲突仍会阻断。本版本不提供自动解除协议，也不保证找回早前实际丢失的数据。失败不代表浏览器绝未提交写入，复制失败也不会清除源证据。
- 两项功能独立提交后合并发布。冻结组合源码通过4271 Node / 84 Python、581项聚焦检查及静态/构建检查。运行白名单仍为130项，无新增权限、存储键、依赖或远端请求。
- 原生浏览器在生产工作区与完整备份组件上验收：未核验/无效记录的复制均零写入并保留名称草稿；已核验复制保留源与恢复副本，新副本不含源操作记录；配置恢复在审阅与确认阶段均阻止未核验操作，原始内容及代际保持不变。仅个人模块的审阅可用且Apply启用，但本次未实际提交该恢复。
- 原生测试使用20份字节一致的生产资源与合成RAM适配器，不是安装扩展或完整Options宿主页。四份记录均无页面错误、网络、提供方、Sync、权限、删除或清空调用；仅已核验复制发生预期的两次RAM写入。注入未核验状态属于明确的脚本测试步骤，不证明磁盘持久性、崩溃行为或真实资料恢复。
- 仅发布GitHub，不上传截图或验收资料，不变更Chrome Web Store上传或提交。

## English

- Add configuration-import receipt admission checks to workspace duplication and Complete local backup restore. Pending, malformed or unsupported receipts block affected operations with explicit guidance and a separate workspace-scoped read-only inspection link, preserving current name or restore drafts.
- Duplication checks the source under the lifecycle lock before creating a copy. It cannot bypass a pending import. A verified source's new copy omits the source operation identity while retaining configuration and complete recovery objects, including ancestry, unchanged. The source remains untouched, and the existing Focus timer reset remains.
- Complete configuration restore checks receipts during review, at restore-lock admission and again after asynchronous recovery preparation. Unresolved imports cannot be overwritten or receive new generation fences through this path. Refusal precedes recovery-slot, staged-bundle and registry writes; receipts are never automatically settled or cleared.
- Legacy single-workspace archives check only the explicitly selected destination. Matching partial configuration restores check matching destination IDs. All-scoped configuration restores check every current workspace, including Trash and IDs the incoming topology would remove. Personal-module-only or global-library-only restores gain no new receipt gate.
- Structurally valid verified receipts remain accepted for duplication and complete restore, including after ordinary edits. Existing extra-confirmation rules for manually importing the same configuration file remain unchanged. Sources without a receipt retain existing behavior.
- An exactly matching unresolved import can first be verified through the original-file Settings flow. Changed-content conflicts remain blocked; this version adds no automatic resolution protocol and does not guarantee recovery of earlier real-world data loss. Failure does not prove the browser never committed, and duplication failure never clears source evidence.
- Two independent feature commits precede this batch release. Frozen combined source passed 4271 Node / 84 Python tests, 581 focused checks, and static/build checks. The runtime allowlist remains 130 files, with no new permissions, stored keys, dependencies or remote requests.
- Native-browser acceptance mounted production workspace and Complete Backup components: pending/invalid duplication preserved name drafts without writes; verified duplication retained the source and recovery content while omitting the source receipt from the clone; pending configuration restores were blocked during review and confirmation with raw content and generations unchanged. Personal-module-only review became available with Apply enabled, but no such restore was committed in this native run.
- Native checks used 20 byte-identical production assets with synthetic RAM adapters, not an installed extension or the full Options host. All four records showed no page errors, network, provider, Sync, permission, remove or clear calls; only verified duplication made its expected two RAM writes. Pending-state injection was explicit scripted test instrumentation, not evidence of disk persistence, crash behavior or real-data recovery.
- GitHub only; no screenshots or QA artifacts uploaded and no Chrome Web Store upload or submission changes.
